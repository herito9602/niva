- [ ] **"Dev mode"**: monitor AI coding agents (Claude Code hooks), TwoCode-style.
- [ ] **Conversation with short memory** (owner's request, 2026-11-10, after the MVP). Niva should hold a short back-and-forth: keep the last few turns in RAM only (never on disk) and expire them after a few minutes; keep listening without the wake word when Niva itself asked a question; and never let an old turn confirm a risky action (a confirmation stays bound to its own prompt). Cost: the prompt grows (prompt evaluation measured at about 0.3 ms per token), so cap the history. Pairs with "Sending WhatsApp messages" above: today Niva has no messaging tool, does not keep listening after a chat reply and has no memory, so the system prompt tells the model not to end a reply with a question or an offer of help; revisit that rule when this lands.
- [ ] **The model sometimes calls `close_app` on requests that are not close requests.** Seen live: the confirmation prompts "¿Cerrar WhatsApp.Root.exe?" and, earlier, "¿Cerrar CalculatorApp.exe?" and "¿Cerrar Notepad.exe?" on commands that did not ask to close anything; the safety gate caught every one, so nothing was closed. The latency log has no text, so the triggering phrases are unknown. Suggested: an opt-in local debug transcript log (off by default, local file, clearly marked as sensitive) to see what was heard and what the model chose, then add the phrasings to the E1 adversarial set.

## Ideas from jarvis (github.com/adewaskar/jarvis, reviewed 2026-11-05)
Read its README, 20 commit messages, `src/lib/vad.ts` and `src/lib/voice.ts`, not a full audit. It runs in a browser with a cloud LLM, so these are ideas, not code. The always-open microphone, audio before onset, discard reasons and truthful `speak_started` were adopted in `speech-io` and task 3.3.
- [ ] **Voice barge-in recipe.** Their layers: echo cancellation, a raised trigger threshold while speaking (2.4x), a 350 ms guard at the start of each sentence (the first syllable is the least cancelled), a filter comparing the heard words with the words being spoken, and override words such as "stop" that always pass. Echo cancellation there comes from the browser; a Python sidecar has to find its own, so this needs a spike first.
- [ ] **Ending a turn on the words, not only on silence.** They hold the turn when the text ends on a function word ("and", "to") or looks unfinished, capped at 6 s, and a finished sentence waits 0 ms. Not adopted: on the only real cut left in `spikes/vad/RESULTS.md` (phrase 15), the fragment before the pause transcribes as "set the volume", which matches no function word, so the rule would not have helped. One sample on CPU; repeat on the GPU with STT in place. A Spanish word list would also be needed.
- [ ] **Slice 5: a sound self-test in `doctor`.** One button that plays a short sound and reports whether audio really reached the device, and whether the microphone hears anything, in plain language.

## From the voice latency work (task 3.5, branch perf/3f-voice-latency, 2026-11-09)

- [ ] **WASAPI low-latency output.** The sound device is opened through MME (sounddevice's default), which adds roughly 160 ms of audible delay on top of what the sidecar measures. Opening the stream with WASAPI (shared mode, small buffer) should remove most of it, but it changes the audio API and the behaviour with other apps playing, so it was left out of the latency work. Try it behind a switch and measure with the speaker-to-microphone loopback, not with the log (the log cannot see it).
- [ ] **Rule-based fast path for the commonest commands.** "volume 30", "mute", "open <app>" could skip the LLM (about 1.1 s of the budget) with a small deterministic parser in the host, falling back to the model when it does not match. Needs the same multilingual coverage as the eval set, and a clear rule for what is NOT safe to shortcut (anything that confirms or closes things).
- [ ] **A trimmed LLM prompt.** The system prompt and tool list are sent on every request; a shorter prompt (or a cached prefix, if Ollama keeps it warm for this model) lowers time to first token. Measure on `eval/commands.yaml` before and after, since the gate is accuracy first.
- [ ] **Pre-generate the template replies.** The reply cache fills lazily, so the first use of each phrase still pays the network. Pre-generating the known templates would make that first use fast too, but it means a burst of requests to the service at startup; do it only if the first-use latency shows up in real logs, spread out and on a background thread.
- [ ] **Pin the voice dependencies.** `voice/pyproject.toml` lists `faster-whisper` and `edge-tts` without versions, but the single-pass Whisper path (`stt.single_pass_decode`) and the persistent websocket (`edge_ws.py`) use their internals (1.2.1 and 7.3.1 were installed). Both fall back to the public APIs when the internals change, and a test fails on a faster-whisper upgrade that drops them, so this is slower, never wrong. Pinning would make that explicit.
